# Per-stage design choices (A2 deliverable)

One row per stage, same shape as the original starter stub. Stages 0-4 are what we
actually built for A2 — every cell there is real and checkable against
`notebooks/kb_demo.ipynb`, `configs/config.yaml`, or the code itself. Stages 5-9 are A3
(RL/RLVR is a bonus, A3 or A4 depending on time), so those rows say when the work lands
and which options we're weighing, not results we don't have yet. We're not claiming
anything unbuilt as done — `retrieval/retriever.py` and friends still raise
`NotImplementedError` on purpose.

Section 7 of `forms/A2_form.docx` asks for the same eight facets in a different layout
(one row per facet, Stages 1-4 folded into a single cell) because that's literally how
the form's own table is built — we checked. The facts here and the facts in the form
should read as two views of the same work, not two different stories.

## The disabled stage — Stage 1, Enhancement

`configs/config.yaml` locks `enhance: {enabled: false, model: "none", type: "none"}`.
`ingest/enhance.py::run()` checks that flag first and hands `pages` back untouched, so the
generative `Enhancer` class never gets constructed and its `NotImplementedError` stubs
never fire.

We turned it off on purpose. A&S is a clean 1964 print scan — even lighting, no
bleed-through, no water damage — so classical preprocessing (deskew, denoise, CLAHE)
already gets the pixels where they need to be. A generative enhancer earns its keep on
scans that are actually degraded, by filling in detail the scan lost. On formula-dense
notation, a model guessing at strokes it wasn't sure about is a real risk to the exact
content we're graded on reading correctly, and our corpus doesn't have the damage that
would justify taking that risk. Flipping it back on is a one-line config change if a
future corpus needs it — the stage keeps its place in the fixed pipeline order regardless.

## Known limitations, stated honestly

- **53 of 1040 pages (5.1%) failed OCR outright** and contribute no chunks: 6 to
  repetition-degeneration on dense tables (real content, permanently lost), 16 partial
  cutoffs, 31 near-empty.
- **Table-value retrieval is the weak point.** A query for the value of J₀ at x=1.2
  ranked an unrelated chunk first and the actually relevant formula second, and the
  ground-truth value table for that range turned out to be under-transcribed upstream
  too, so the failure stacks in two places. Formula and definition queries work well —
  "exponential integral Ei(x)" returns the right page and formula at rank 1, score 0.698.
- **Don't quote the raw "24.6% of words indexed" number.** It's wrong in both
  directions at once: our own numerator is deflated because LaTeX-packed table cells
  count as fewer "words" under a plain `.split()` (8.9 chars/word against prose's usual
  5-6), while the archive's denominator is inflated because its old OCR splits single
  decimal numbers into several tokens on the same table-heavy pages. Page coverage,
  987/1040 = 94.9%, is the number that actually means what it says.
